## 1. 用你的场景回答：现在加一个 OpenRouter Platform，会怎样

先对齐概念（需求里的说法 ↔ 代码里的东西）：

| 需求里的说法 | 代码里对应的东西 |
|---|---|
| Platform 模板 | 一个实现了 `PlatformQuotaAdapter` 的类（现在只有 `ZenMuxAdapter`） |
| Platform 实例（用户新建） | `platformInstances.<id>`，其 `type` 指向某个模板 |
| 绑定到 LLM Provider | `providerBindings[providerId] = <instanceId>` |

**一句话结论**：判定与恢复的**引擎**确实可以「照接口实现即插即用」（已实测，见第 1 步）；
但今天的「Platform 模板」不是一个完整的东西——**它没有自己的端点、没有自己的注册位置、
也没有任何办法让 UI 知道它存在**。所以 OpenRouter 加进来只能当「二等公民」。

### 假设你今天就动手加 OpenRouter，逐步会发生什么

| 步骤 | 你要做的事 | 结果 |
|---|---|---|
| 1 | 写 `src/platforms/openrouter.ts`，实现 3 个方法 | ✅ **完全如你所愿**。实测：一个只实现接口的假平台 `acme`，被状态机正确驱动跑通「配额错误 → 查统计 → 等待 → 重发」全链路，`index.ts`/`state.ts`/`recovery.ts` 一行没改 |
| 2 | 让它被系统认识（注册） | ⚠️ **「实现接口」不够**：必须额外写注册代码——要么改核心文件 `src/index.ts:77`（那里硬编码了 `this.adapters.set('zenmux', new ZenMuxAdapter())`），要么另写一个插件调用 `ctx.quota.registerPlatformAdapter(...)` |
| 3 | 在 `cordis.yml` 里预先写好 OpenRouter 实例 | ❌ 插件**启动即报错** `unknown platform type "openrouter"`。配置校验发生在注册之前，没有任何时序能绕过（探针 A） |
| 4 | 让 OpenRouter 请求 openrouter.ai，而不是 zenmux.ai | ❌ **结构性阻塞**：全插件只有一个全局 `platformBaseURL`，实例配置里没有 `baseURL` 字段。你的 OpenRouter 适配器会被要求去请求 `https://zenmux.ai`（探针 D）；改成 openrouter.ai 又会把 ZenMux 实例一起改坏 → **两个平台无法并存** |
| 5 | 让用户在 UI 里新建 OpenRouter 实例并绑定 provider | ❌ 下拉框写死只有 `zenmux` 一个选项（`InstanceCard.tsx:246`），host 也没有「列出已注册平台」的接口（只有 `providers.list`）→ 用户**看不到、也建不了** OpenRouter 实例 |
| 6 | 如果 OpenRouter 需要额外参数（额外 header、多把 key、org id 等） | ❌ `fetchQuota(credential, baseURL, signal)` 只拿到这三样，**看不到实例配置**，没有通道 |

### 所以对着你的需求，答案是

- 「照着接口去实现方法」→ ✅ 能做出一个**被状态机正确调用**的 OpenRouter 适配器。这是真实成立的。
- 「便可以新加一个 Platform 模板」→ ❌ **不能**。还差三样：**注册位置**（第 2 步）、
  **端点归属**（第 4 步，且是结构性阻塞）、**UI 可见性**（第 5 步）。第 3、6 步是附带缺口。

根因可以归成一句：**「Platform 模板」目前没有身份**——模板 = 一个 adapter 类 + 一行硬编码注册。
要让它成为真正的一等模板，模板得能自己声明「我是谁、我的默认端点在哪、我有哪些专属配置项」，
并且这个声明要能被注册点和 UI 读到。这就是 §7 那 6 项改造在补的东西。

**好消息**：缺口全部是**接口扩容 + 一处字段搬家 + 一个列表接口**，不涉及状态机重写，
也不需要动 DSH 框架。

### 判定摘要

| 判断 | 结论 | 依据 |
|---|---|---|
| 恢复状态机是否与平台解耦 | ✅ **是，且实测可复用** | 探针 B/E |
| 「实现几个固定方法即可新加模板」是否成立 | ❌ **否**：缺注册位置、端点归属、UI 可见性 | 上表第 2/4/5 步 |
| 接口本身是否够小、够稳定 | ✅ **是**（3 方法 + 1 字段） | `src/platform.ts:24-39`，与 v1 §8.1 逐字一致 |
| 是否达到了 v1 §19.2 / README / AGENTS.md 承诺的程度 | ❌ **文档过度承诺** | §8 列出 4 处需改措辞 |

## 3. 现状：接口与调用链

### 3.1 接口（`src/platform.ts:24-39`，与 v1 §8.1 一致）

```ts
interface PlatformQuotaAdapter {
  readonly platform: string
  matchesQuotaExhausted(failure: LlmFailure): boolean
  fetchQuota(credential: string, baseURL: string, signal: AbortSignal): Promise<PlatformQuotaSnapshot>
  resolveWaitTarget(snapshot: PlatformQuotaSnapshot): number | null
}
```

归一化快照为 `windows: QuotaWindow[]`（`name` / `usagePercentage` / `remainingFlows` / `resetsAt`）。

### 3.2 判定链（`src/index.ts:213-235`）

```
payload.provider → config.providerBindings[provider] → instanceId
  → config.platformInstances[instanceId] → instance.type
  → this.adapters.get(instance.type) → adapter.matchesQuotaExhausted(failure)
```

- 任一环节缺失 → `next()`（fail-safe，不吞别人的错误）——`index.ts:222,224,231,232`。
- 状态、`disabled`、统计单飞全部按 **instanceId** 键控（`index.ts:67,150,309`），同平台多实例天然隔离。

### 3.3 注册点

- 构造期硬编码一个内置平台：`this.adapters.set('zenmux', new ZenMuxAdapter())`（`index.ts:77`）。
- 公开注册：`registerPlatformAdapter(adapter)`（`index.ts:167-178`），基于 `ctx.effect`，返回 disposer。
- **实测确认**：外部插件可通过 `ctx.inject(['quota'], c => c.quota.registerPlatformAdapter(adapter))`
  在**零核心改动**下注册新平台（探针 E），且 `dispose()` 后该平台立即失效（探针 C）。

## 5. 缺口清单

### P0-1 · `platformBaseURL` 全局唯一，两个平台无法各自持有一个端点 —— ✅ 已解（§7-1）

- **现象**：`platformBaseURL` 是顶层配置（`config.ts:60,90`），实例 schema **没有** `baseURL` 字段
  （`config.ts:67-87`）。统计查询时把全局值传给适配器（`index.ts:313` →
  `recovery.ts:72` → `adapter.fetchQuota(credential, baseURL, signal)`）。
- **证据**：探针 D —— `acme` 实例的 `fetchQuota` 收到的是 `https://zenmux.ai`；实例配置里没有任何
  字段可以覆盖它。
- **影响**：接入任何**官方地址不是 zenmux.ai** 的平台，只能改全局 `platformBaseURL`，而这一改会同时
  改变 zenmux 实例的行为 → **两个平台无法在同一个部署里并存**。这是「真·多平台」的结构性阻塞。
- **文档冲突**：v2 §2.1 写「`platformBaseURL`：平台 URL **由平台模板决定**，对某个实例没有区分意义」，
  但实现里模板根本不持有 URL，URL 是用户手填的全局值。

### P0-2 · base 层（`cordis.yml`）无法声明新平台：校验早于注册 —— ✅ 已解（§7-3，改为加载期告警 + 写入期严格）

- **现象**：`validateConfig(config, this.platformNames())` 在**构造函数**里执行（`index.ts:80`），
  而 `platformNames()` 此刻只含内置 zenmux（`index.ts:77`）。第三方注册必须等到插件 mount 之后。
- **证据**：探针 A —— 配置里直接写 `type: 'acme'` → `mount()` 抛 `unknown platform type "acme"`，
  **无任何时序可以让注册先发生**。
- **影响**：新平台实例**不能**写在 `cordis.yml` 的 base 层，只能等系统起来后由 UI/`settings.yaml`
  （user 层）写入。对「在配置文件里一次性声明」的使用方式是硬阻塞。
- **注意**：settings 写入路径反而是好的——它用实时 adapter 集合校验，注册后即可写入成功（探针 B）。

### P0-3 · Client UI 硬编码 zenmux，非 zenmux 实例无法从 UI 创建 —— ✅ 已解（§7-4）

- **现象**：
  - 下拉只有一个选项：`<option value="zenmux">zenmux</option>`（`InstanceCard.tsx:246`）；
  - 新实例草稿默认 `type: 'zenmux'`（`InstanceCard.tsx:41,56`）；
  - 文案硬编码 `ZenMux 管理 API 密钥`（`locales.ts:24,69`）；
  - host 只暴露 `settings.get` / `settings.update` / `providers.list`（`index.ts:442-486`），
    **没有 `platforms.list`**，client 无从发现已注册平台。
- **影响**：即使后端注册了新平台、`settings.yaml` 里也写好了实例，用户**无法在 UI 中新建或改类型**；
  改动 client 还必须重新 bundle。
- **补充**：`DEFAULT_PLATFORM = 'zenmux'`（`config.ts:3`）与 `DEFAULT_PLATFORM_BASE_URL`（`config.ts:4`）
  也是泛化模块里的平台知识泄漏。

### P1-1 · 适配器拿不到实例配置：平台专属参数没有通路 —— ✅ 已解（§7-2，`fetchQuota(context)` + `instance.options`）

- **现象**：`fetchQuota(credential: string, baseURL: string, signal)` 只收到**一个字符串凭据 + 一个
  URL**；适配器看不到 `PlatformInstanceConfig`（`index.ts:310-317` 只传这三个值）。
  `PlatformInstanceConfig` 本身也是封闭的固定字段集（`config.ts:44-55`）。
- **影响**（任何一个都足以卡住真实平台接入）：
  - 需要多凭据（API key + org/project id，如 OpenAI 的 `OpenAI-Organization`）；
  - 需要额外 header 或查询参数；
  - 需要账号/租户标识；
  - 需要平台专属的等待参数（例如「冷却 N 分钟」而不是 `resetsAt`）。
- **现状兜底**：探针确认未知字段能存活到 config 对象里，但**没有任何代码读它们、也没有类型**，
  等于要绕过公开接口去 `currentConfig()` 里掏——不可接受。

### P1-2 · 适配器不能声明自己的配置 schema / 默认值 / 展示名 —— ✅ 已解（§7-2，`optionsSchema` / `defaultBaseURL` / `label`）

接口里没有 `label`、`defaultBaseURL`、`configSchema`、`validateCredential`。后果是平台知识被迫
外溢：`config.ts` 必须写死默认平台与默认 URL，client 必须写死下拉项与文案，
host 无法把「有哪些平台、叫什么名字、默认端点是什么」告诉 UI。

### P1-3 · 「耗尽」语义写死在通用层 —— ✅ 已解（§7-2，可选 `isExhausted`）

`decideWaitAction`（`recovery.ts:141`）用通用函数 `isSnapshotExhausted` → `isWindowExhausted`
（`platform.ts:42-48`），判据固定为 `usagePercentage >= 1 || remainingFlows <= 0`。
平台若用别的口径（例如「套餐已到期」但用量显示 0.5，或数值方向相反），只能**在构造快照时
把数字伪造成 1/0**，属于隐式约定、不可自证。接口上应允许适配器直接给出 `isExhausted`。

### P2 级

- ~~**P2-1 · 没有任何适配器契约测试**~~ ✅ 已解（§7-5，`tests/platforms/contract.spec.ts`）：
  改造前 `registerPlatformAdapter` 零用例、`tests/platforms/` 只有 `zenmux.spec.ts`。
- ~~**P2-2 · 平台常量散落**~~ ✅ 已解：`DEFAULT_PLATFORM` / `DEFAULT_PLATFORM_BASE_URL` 已删除，
  zenmux 端点移入适配器；client 下拉与文案改为数据驱动/通用文案。
- **P2-3 · 未知实例字段静默通过**（§4 第 6 条实证）：⚠️ 部分解决——平台专属字段现在有正式容器
  （`instance.options` + 适配器 `optionsSchema`，会 fail loud）；实例级未知字段仍按 schemastery
  行为透传，未加严格模式。
- **P2-4 · 无凭据校验/连通性测试钩子**：`fetchQuota` 失败与「key 写错」无法区分，都会走 1 小时退避后
  `disabled`，用户从 UI 只看到卡片不变（可考虑可选 `validateCredential` 或把统计失败的
  401/403 直接归类为凭据错误）。
- ~~**P2-5 · `type` 有默认值**~~ ✅ 已解：`type` 改为必填（schema `.required()`）。

## 6. 现实检验：改造前接入一个平台到底要改什么

> 以下是**改造前**的结论，改造后见 §0。

| 方案 | 需要改动 | 能否「只实现接口」 |
|---|---|---|
| **A. 最小可行**（与 zenmux 共用 baseURL、用户手写 `settings.yaml`、不要求 UI） | ① 新增 `src/platforms/acme.ts`；② 一个注册插件（`ctx.inject(['quota'])`，探针 E 已验证可行） | ⚠️ **勉强算**——前提是接受 P0-1/P0-2/P0-3 三个限制 |
| **B. 现实可用**（用户能在 UI 里建、能用不同端点） | A + ③ `InstanceCard.tsx` 下拉与默认值；④ `locales.ts` 文案；⑤ 若端点不同还要动全局 `platformBaseURL`（等于不能与 zenmux 并存） | ❌ 需改 3~5 处，且第 ⑤ 项无解 |

即：**「不改恢复状态机」为真**（值得肯定的设计成果）；**「只需实现几个固定方法」为假**。

## 7. 建议的改造（按性价比排序，均不动状态机）——已全部实施（见 §0）

1. **baseURL 下沉到适配器 / 实例**（解 P0-1）
   - `PlatformQuotaAdapter` 增加 `readonly defaultBaseURL?: string`；
   - `PlatformInstanceConfig` 增加可选 `baseURL?: string`；
   - 解析顺序：`instance.baseURL` ?? `adapter.defaultBaseURL` ?? 顶层 `platformBaseURL`（保留为
     legacy 全局覆盖，兼容现有配置）。
2. **接口扩容**（解 P1-1/P1-2/P1-3，破坏式但包内可控）
   - `fetchQuota(ctx: { credential, baseURL, instance, signal })`（把实例透传给适配器）；
   - 可选 `label: string`（UI 展示名）、`configSchema?`（合并进 `instanceSchema`）、
     `isExhausted?(snapshot)`、`validateCredential?`。
3. **注册时机**（解 P0-2）
   - 把「未知平台类型」的 fail loud 从构造函数推迟到 `settings` 就绪 / 首次判定时（判定链已有
     `!adapter → next()` 的兜底）；或提供配置驱动的适配器加载（`cordis.yml` 里声明适配器模块）。
4. **`platforms.list` API + UI 数据驱动**（解 P0-3）
   - host 在 `/auto-continue/api` 增加 `platforms.list`（返回 `{ id, label }[]`），client 下拉改为
     渲染该列表、`type` 默认取列表首项；`locales.ts` 的 ZenMux 专属文案改为由 `label` 填充。
5. **补适配器契约测试**（解 P2-1）
   - 把本次探针固化为 `tests/platforms/contract.spec.ts`：用一个最小假平台跑通全状态机 +
     未注册类型 fail loud + dispose 失效；这样「接口够用」从此有回归保护。
6. **未知字段 fail loud**（解 P2-3）：给 `instanceSchema` 加严格模式，或至少对已知的拼写近似项报错。

> 其中 1、3 是**新增平台能否真正落地**的分水岭：不解决，多平台只能停留在「同端点、纯手改配置」。

## 9. 附录：探针与复现

探针为临时文件 `tests/__scratch-platform.spec.ts`（本次审查后已删除，避免污染测试基线）。
核心是下面这个**只实现接口 3 方法 + 1 字段**的适配器，以及 5 个用例：

```ts
class AcmeAdapter implements PlatformQuotaAdapter {
  readonly platform = 'acme'
  seenBaseURL: string | undefined
  matchesQuotaExhausted(f: LlmFailure) { return /acme_quota_spent/.test(f.message) }
  async fetchQuota(credential: string, baseURL: string, signal: AbortSignal) {
    this.seenBaseURL = baseURL
    return { windows: [{ name: 'monthly', usagePercentage: 1, remainingFlows: 0,
      resetsAt: new Date(Date.now() + 60000).toISOString() }] }
  }
  resolveWaitTarget(s: PlatformQuotaSnapshot) { return Date.parse(s.windows[0]!.resetsAt!) }
}
```

| 用例 | 断言 | 结果 |
|---|---|---|
| A | base 层配置引用 `acme` → mount 抛 `unknown platform type "acme"` | ✅ 抛错（P0-2） |
| B | mount 后 `registerPlatformAdapter` + `settings.replace` 写入 → 402 走完全链路返回 `{kind:'retry'}` | ✅ 通过（状态机通用） |
| C | 写入未注册类型 → 抛错；`dispose()` 后该 provider 不再被处理 | ✅ 通过 |
| D | `acme.fetchQuota` 收到的 `baseURL` == 全局 `https://zenmux.ai` | ✅ 复现 P0-1 |
| E | 独立插件 `ctx.inject(['quota'], c => c.quota.registerPlatformAdapter(adapter))` → 链路可用 | ✅ 零核心改动可注册 |

复现方式：把 §9 的 `AcmeAdapter` 与 `MemorySettingsProvider`（见 `tests/settings.spec.ts`）拼成
一个 `tests/*.spec.ts`，`npx vitest run <file>`。
