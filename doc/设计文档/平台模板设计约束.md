# 平台模板设计约束

> **性质**：设计约束文档。本文只描述**不变的设计要求与思想**，不描述实现。
> 具体的接口签名、字段名、文件位置与内部机制会随版本演进，**不属于本文的约束内容**；
> 了解当前实现请看 `README.md` 与 `doc/` 下的其余文档。
>
> **用语**：**必须**（硬性要求，违反即视为设计缺陷）、**不得**（禁止）、**应当**（原则上遵守，
> 偏离需有明确理由）。本文以「平台」指代本插件所支持的 LLM 服务商，「宿主框架」指运行本插件的
> 框架（DeepSeek Harness）。

---

## 1. 运行目标

插件要解决的是一个**与平台无关**的问题：让一次因为「平台订阅配额耗尽」而失败的 LLM 请求，
在配额恢复之后自动重新发送，对用户表现为「这次请求只是慢了一点」。

为此它必须完成四件事：

1. **识别**——判断一次请求失败是否属于「配额耗尽」这一类**可恢复**的失败；
2. **确认**——查清该账号的配额状态，以及配额何时恢复；
3. **等待**——在不阻塞进程、且随时可取消的前提下等到恢复时刻；
4. **续跑**——在**同一个 turn/step 内**促使原请求重新发送；可选地先注入一条说明，
   让模型知道刚刚发生过等待。

它的边界同样是设计的一部分：

- **宁可放弃，不可猜测**：四个环节中任一环节无法确定（认不出、查不到、算不出、等不到），
  插件必须放弃并把失败照常上抛；不得用猜测出来的时间继续等待，也不得无限等待。
- **不误伤**：不属于本插件负责的失败，必须原样交还给宿主框架的其他处理者，
  不得吞掉，也不得改变其语义。
- **不越界**：只处理进程内、当前请求范围内的事；不做跨进程恢复、不轮询额度、不预先拒绝新请求。
- **无感**：不得要求用户重新提问，也不得改动会话已有的可见内容（可选的那条等待说明除外）。

## 2. 三个角色及其关系

| 角色 | 是什么 | 与账号的关系 |
|---|---|---|
| **Platform 模板** | 一种「如何与该平台打交道」的**能力**：如何识别它的配额耗尽失败、如何查它的配额、如何算出恢复时刻 | 与账号无关，可被任意多个账号复用 |
| **Platform 实例** | 某个平台上的**一份具体账号配置**：凭据、端点、平台专属参数，以及该账号的恢复策略与提示偏好 | 必须恰好归属一个模板 |
| **LLM Provider 实例** | 宿主框架中的 LLM 路由入口 | 通过绑定指向一个实例 |

关系约束：

1. **模板 : 实例 = 1 : N**。一个模板可以生成任意多个实例；每个实例必须恰好归属一个模板。
2. **实例 : Provider = 1 : N**。一个 Provider 必须且只能绑定一个实例；一个实例可以被多个
   Provider 绑定。
3. **未绑定实例的 Provider，插件不得介入**——它必须表现得像本插件不存在。
4. **恢复的记账单位是实例**：同一实例下的多个 Provider 共享等待状态与「放弃」状态；
   不同实例之间完全独立。记账既不按 Provider，也不按模板。
5. 两个直接结论：
   - 「同一平台的多份账号」= 同一模板下的多个实例；
   - 「多个平台并存」= 多个模板 + 各自的实例，彼此互不干扰。

## 3. 接入新平台的两条硬性要求

### 3.1 第一条：接入新平台不得影响架构中的其他代码

接入一个新平台时，允许的改动**只有两处**：

1. 提供该平台的一份**模板实现**；
2. 把这份实现**注册**给插件。

除此之外不得有第三处改动。具体地，不得改动：失败判定与恢复流程、等待与取消机制、
插件对外的服务/事件/配置与设置系统、管理界面，以及**任何既有平台**的实现。

由此必须满足的推论：

- **平台之间互不感知**：新平台的加入不得改变既有平台的行为；
- **通用层不得包含平台知识**：通用代码中不得出现任何具体平台的名称、默认地址、字段名、
  错误文案、配额口径或类似判断；
- **通用层不得为某个平台开口子**：不允许「如果是某平台就……」这类分支；
- **差异只能通过契约表达**：若某个平台的需求在契约里表达不出来，正确的做法是**扩展契约**，
  而不是在通用层里写特例。

这条要求是整套设计的目的：**新增平台是可预期的常规操作，而不是需要理解并修改核心流程的高风险改动。**

### 3.2 第二条：隔离必须由接口契约在结构上保证

「不影响其他代码」不能只靠约定俗成，必须由一个**稳定的接口契约**强制保证。
契约的设计要求如下：

1. **接入方式唯一**：插件只接受「一个满足契约的对象」作为平台实现；不得要求特定的实现形态
   （语言构造、类或普通对象、文件与模块布局均不受限）。
2. **契约自足**：契约必须覆盖通用层在**不认识任何平台**的前提下完成第 1 节运行目标所需的全部信息，
   至少包含四类能力——
   - **身份**：模板的标识，实例据此指向它；
   - **判定**：给定一次失败，是否属于本平台的「配额耗尽」；
   - **查询**：按给定的凭据与端点，取得该账号的配额状态；
   - **决策**：由配额状态得出「何时可以重试」。
3. **可选的表达能力**：契约还应当允许模板声明与自身相关的展示信息、默认端点、专属参数规则，
   以及无法用统一口径表达的「耗尽」判定。这些可选项的取舍可以随版本变化，
   但**不得**因为它们的增减而让通用层认识具体平台。
4. **输入受控**：模板只能看到插件**显式交给它**的输入（凭据、解析后的端点、该实例的配置）；
   模板不得反向依赖插件内部结构、不得读写插件的共享状态、不得假定自己被调用的时机与次数。
5. **输出统一**：模板必须把平台私有响应翻译成插件约定的**统一数据形状**后再返回；
   通用层只处理这个形状，不解析任何平台原始响应。
6. **失败即未知**：模板内部出错等同于「无法确定」，插件据此走放弃路径；
   模板不得用编造的数据诱导插件进入等待。
7. **可注销**：注册必须可撤销；撤销后该模板立即不再参与判定，且不影响其他模板。

### 3.3 由这两条衍生的其他要求

- **可验证性**：必须能用一份「假平台」实现验证隔离是否成立——在不接入任何真实平台的前提下，
  完整跑通「识别 → 查询 → 等待 → 续跑」，并证明通用层没有被改动。
- **注册时机与配置合法性解耦**：实例配置的**结构性**错误必须立即拒绝；但「模板是否已经注册」
  不得成为配置能否存在的先决条件——允许先声明、后注册；未注册期间该实例不得被处理，
  且不得导致插件启动失败。
- **默认值归属**：与平台相关的默认值（例如默认端点）只能由模板声明，实例可以覆盖；
  通用层不得为任何平台预置默认值。
- **凭据中立**：插件只负责解析与传递凭据，不解释其格式；对凭据格式的要求（如有）属于模板。
- **实例不混平台**：一个实例只属于一个模板；需要多份账号就新建多个实例，
  不得在同一个实例内切换或混合多个平台。

## 4. 不变量（可验收）

以下每一条被破坏，都属于**设计缺陷**，而不是「实现细节上的取舍」：

1. 通用层中不存在任何具体平台的名称、默认值或专属分支。
2. 接入一个新平台，除「新增一份模板实现 + 注册」外不改动任何既有代码；既有平台行为不变。
3. 每个平台实现可独立注销，注销不影响其他平台。
4. 契约表达不了的需求，应当扩展契约，而不是在通用层加特例。
5. 平台实现不依赖插件内部状态，也不假定被调用的时机与次数。
6. 恢复状态以实例为单位记账，不同实例互不影响。
7. 任一环节无法确定时，插件放弃等待，并把失败照常上抛。
8. 等待过程可被取消，且取消不改变共享状态。
9. 未绑定实例的 Provider，其行为与「本插件不存在」时一致。
10. 上述性质可以用一份假平台实现完整验证，不依赖任何真实平台。
