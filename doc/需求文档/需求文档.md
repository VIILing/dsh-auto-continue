## 1. 背景与问题

### 1.1 问题

当 DeepSeek Harness 中某个 provider 因**订阅配额耗尽**而返回错误时（不同平台的错误形态不同，
v1 为 ZenMux 的 HTTP 402 `quote_exceeded`），agent loop 默认把该失败当作普通错误结束本轮。
用户希望：

1. 插件识别这类「配额耗尽」错误；
2. 查询该 provider 对应平台的配额接口，得到配额窗口与重置时间；
3. 在进程内等待配额重置；
4. 等待结束后，让 agent loop **在同一个 turn/step 内**重发最后一次失败的请求，使模型对
   「发生过失败与等待」无感；
5. 可选地在重发前注入一条提示，说明距上次请求已经过了多久。

### 1.2 目标平台

LLM 服务提供商众多，首版只对 **ZenMux** 一个服务商做平台适配，以完成初版验证。

**但本插件在需求上不是 ZenMux 专用插件**：任何能提供配额信息的服务商，都应当能够在不修改
核心流程的前提下接入。这条要求本身是硬性的，见 §5.2 NFR-7。

- LLM 协议：OpenAI Chat Completion（由 DSH 的 `dsh-llm-pi-ai` 以 `api: openai-completions` 承载）。
- 首版适配平台：ZenMux。
- 首版平台配额接口：`GET https://zenmux.ai/api/v1/management/subscription/detail`。

### 1.3 首版平台（ZenMux）的关键事实

- 402 有三种错误类型：`quote_exceeded`（订阅配额耗尽，**本插件只处理这一种**）、
  `insufficient_credit`（账户逾期）、`reject_no_credit`（余额不足）。
- 配额接口返回 **5 小时**与 **7 天**两个滚动窗口，含用量比例、剩余额度与重置时间。
- 配额接口使用 **Management API Key** 鉴权（`Authorization: Bearer <key>`）。
- 月限额满时，7 天窗口也会满（需求方确认的前提）。

> **核对状态**：上述 402 结构与配额响应样例最初来自需求方描述。真实统计响应已核对完毕
> （见 §7 验收第 17 条）；402 识别规则已用需求方提供的**线上抓取的真实 402 响应体**
> （`quote_exceeded`）核对完毕（见 §7 验收第 18 条）。此外需求方还提供了账号**达到配额上限**
> 时的真实统计响应，用于覆盖此前从未被测到的「窗口已耗尽」分支。

## 2. 目标与成功标准

### 2.1 功能目标

| 编号 | 目标 |
|---|---|
| G1 | 识别已配置 provider 的配额耗尽错误（v1 为 ZenMux 402 `quote_exceeded`） |
| G2 | 查询平台配额接口，算出需要等待到什么时候 |
| G3 | 在进程内等待配额重置，并在同一 turn/step 内无感重发 |
| G4 | 配额接口暂时失败时按退避重试，超过总时长上限则放弃并禁用该实例的续跑 |
| G5 | 等待重置后重发仍失败时，进入有限次、总时长受限的宽容退避重试 |
| G6 | 可选注入一条提示消息，说明等待时长 |
| G7 | 不修改 DSH 其他包，插件完全独立 |
| G8 | 设计上为未来「配额耗尽后切换 provider」预留空间 |

### 2.2 成功标准

1. 插件以独立包形式安装并启用后，对已配置凭据的实例，其 provider 的配额耗尽场景可自动等待并续跑。
2. 续跑对模型完全无感：模型历史不包含失败请求与等待本身（除非开启提示）。
3. 对未配置凭据的 provider、未绑定实例的 provider、非配额耗尽错误，插件行为与未安装时一致。
4. 全部测试通过，验收标准见 §7。

## 3. 非目标（明确不做）

- 不跨进程重启恢复。
- 不轮询额度，不预停新请求。
- 不处理余额类／账户逾期类错误（v1 ZenMux 中为 `insufficient_credit` / `reject_no_credit`）。
- 不实现 provider 切换（只预留事件与扩展点）。
- 不使用 `system/message` surface 事件承载通知（该 surface 事件是系统提示词槽位，
  不承载插件通知；见 §8），不改 DSH core。
- 不展示实例的实时运行状态（如等待倒计时）。

## 4. 术语表

| 术语 | 解释 |
|---|---|
| provider | `ctx.llm` 中注册的路由名，请求通过它选择模型服务 |
| Platform 模板 | 一种「如何与该平台打交道」的能力（识别、查询、决策），与账号无关 |
| Platform 实例 | 某个平台上的一份具体账号配置（凭据、端点、专属参数、恢复策略） |
| Platform Key / Management Key | 调用平台配额接口所需的管理密钥 |
| 配额接口 | 平台提供的配额查询接口 |
| 配额窗口 | 平台的滚动配额窗口；v1 ZenMux 为 5 小时窗口与 7 天窗口 |
| 耗尽 | 配额窗口已用尽 |
| 无感重发 | 在同一 turn/step 内由 agent loop 重试，模型看不到失败与等待 |
| 统计滞后 | 配额接口数据与实际 API 行为不一致 |
| disabled | 本插件对某实例在本次进程生命周期内不再自动续跑 |
| resumeNotice | 可选的重发前提示消息 |

## 5. 需求清单

### 5.1 功能需求（FR）

| 编号 | 需求 | 说明 |
|---|---|---|
| **FR-1** | 识别配额耗尽错误 | 只把「配额耗尽」这一类**可恢复**失败纳入处理；判定规则属于平台模板，通用流程不得内置平台措辞 |
| **FR-2** | 查询配额状态 | 通过平台配额接口取得该账号的窗口用量与重置时间；查询失败按 FR-6 处理 |
| **FR-3** | 等待配额重置 | 等待必须可随时取消、不阻塞进程、不使用不可中断的长睡眠 |
| **FR-4** | 同一 turn/step 内重发 | 等待结束后促使 agent loop 重发原请求；不得要求用户重新提问 |
| **FR-5** | 可选的重发前提示 | 开启后，在**首次**等待并重发之前注入一次说明；同一次恢复过程内不重复注入；关闭时不得产生任何模型可见内容 |
| **FR-6** | 失败退避与放弃 | 配额接口暂时不可用时按退避重试，超过总时长上限后放弃并停止该实例的续跑；等待重置后重发仍失败时进入有限次数、有限总时长的宽容退避；两者耗尽后均放弃，并把失败照常上抛 |
| **FR-7** | 恢复成功后的复位 | 重发成功后，该实例回到正常状态，后续配额耗尽可重新进入恢复流程 |
| **FR-8** | 多账号与多平台并存 | 同一平台的多份账号、以及多个平台，必须能够同时配置并各自独立工作；一份账号的配额耗尽不得影响其他账号 |
| **FR-9** | 可配置与可视化 | 用户应当能通过配置文件与图形界面完成：新增／修改／删除账号配置、填写凭据（可选端点与平台专属参数）、把 provider 绑定到某个账号；界面不得要求用户理解任何平台的内部细节 |

### 5.2 非功能需求（NFR）

| 编号 | 需求 | 说明 |
|---|---|---|
| **NFR-1** | 不误伤 | 不属于本插件负责的失败必须原样交还给框架的其他处理者，不得吞掉或改变语义 |
| **NFR-2** | 宁可放弃，不可猜测 | 识别、查询、算时间、等待任一环节无法确定时，必须放弃并把失败照常上抛；不得用猜测的时间等待，也不得无限等待 |
| **NFR-3** | 一切等待可取消 | 用户中止本轮、或插件被卸载时，所有等待与在途查询必须停止；取消**不得**改变共享状态（不因此放弃该实例） |
| **NFR-4** | 凭据安全 | 明文密钥不得在日志、事件或界面响应中回显；界面留空表示「不修改」 |
| **NFR-5** | 配置 fail loud | 实例的结构性错误必须立即报错，不得静默使用默认值；平台专属参数由对应平台模板校验 |
| **NFR-6** | 无残留 | 插件卸载后不得残留定时器或进行中的自动续跑任务 |
| **NFR-7** | 可扩展性：接入新平台不影响其他代码 | 接入一个新平台，只允许「提供该平台的一份模板实现 + 把它注册进来」两处改动；不得改动恢复流程、等待与取消机制、对外服务与事件、配置与设置系统、界面，以及任何既有平台的实现。由此必须做到：通用代码中不含任何具体平台的名称、默认地址、字段或专属判断；平台之间的差异只能通过接口契约表达，契约表达不了时应扩展契约，而不是在通用层写特例 |
| **NFR-8** | 可验证性 | 上述隔离性质必须能用一份「假平台」实现完整验证，不依赖任何真实平台 |
| **NFR-9** | 可观测性 | 关键状态变化（识别成功、开始等待、放弃、追加提示失败等）必须有日志；实例状态变化必须广播事件，供未来策略使用 |
| **NFR-10** | 运行边界 | 仅进程内有效（重启不恢复）；等待期间该会话处于 open turn，`ctx.sessions.fork` 会被拒绝；等待期间用户新消息排队，等待结束后继续处理 |
| **NFR-11** | 尊重宿主框架 | 不修改 DSH 任何其他包，全部通过公开扩展点集成；依赖版本按仓库约定锁定 |

> NFR-7 与 NFR-8 的完整设计要求（含接口契约必须覆盖的能力、隔离的边界与不变量清单）见
> `doc/设计文档/平台模板设计约束.md`。

## 6. 角色与关系

```
Platform 模板（能力，与账号无关）
      │ 由模板生成实例
      ▼
Platform 实例（某平台的一份账号配置）
      │ 被 provider 绑定
      ▼
Provider（宿主框架的 LLM 路由入口）
```

| 关系 | 约束 |
|---|---|
| 模板 : 实例 | 1 : N。一个模板可生成任意多个实例；每个实例必须恰好归属一个模板 |
| 实例 : Provider | 1 : N。一个 Provider 必须且只能绑定一个实例；一个实例可被多个 Provider 绑定 |
| 未绑定实例的 Provider | 插件不得介入，行为与未安装时一致 |
| 恢复状态 | 以**实例**为记账单位：同实例的多个 Provider 共享等待与放弃状态；不同实例完全独立 |

由此得出：同一平台的多份账号 = 同一模板下的多个实例；多平台并存 = 多个模板 + 各自的实例。
（模板 / 实例 / Provider 之间更细的设计约束见 `doc/设计文档/平台模板设计约束.md`。）

## 7. 验收标准

**通用**

1. 全部单元／集成／界面测试通过。
2. 插件包可独立构建、发布，可通过 `dsh plugin add` 或补丁方式启用。
3. 除本包外，不修改 DSH 仓库其他包源码。
4. 配置字段均有校验与默认值；非法配置 fail loud。
5. 所有等待可取消；插件卸载后无残留定时器与进行中的任务。
6. 实例状态变化事件按实例发布。
7. `README.md` 说明配置方式、示例、限制与扩展点。

**恢复行为**

8. 对绑定到已配置凭据实例的 provider，ZenMux 402 `quote_exceeded` 可自动等待并续跑。
9. 未绑定实例、实例无凭据、非配额耗尽错误：行为与未安装插件一致。
10. 配额接口失败退避、等待重置、重发后宽容退避、放弃并停止续跑等行为符合需求（FR-6/FR-7）；
    维度按实例（FR-8）。
11. 取消本轮或卸载插件时，等待立即停止且不改变共享状态（NFR-3/NFR-6）。

**多平台与扩展性**

12. 同一实例下的多个 provider 共享恢复状态；放弃状态影响该实例下所有 provider。
13. 接入一个**不在内置清单中**的平台，仅通过「提供模板实现 + 注册」即可跑通完整恢复流程；
    既有平台行为不变（NFR-7/NFR-8）。

**界面**

14. 界面可独立构建并随插件启用而出现；账号配置的增删改、provider 绑定交互符合 §5.1 FR-9。
15. 删除实例、修改绑定等设置变更的生效语义符合设计文档（见 §9 对照表）。
16. 明文密钥不回显，留空不修改（NFR-4）。

**黄金样本**

17. 用一次**真实**配额接口响应做「黄金样本」核对，锁定字段映射与查询链路（已完成；
    含健康账号与达到配额上限两份真实响应）。
18. 用一次**真实** 402 响应核对识别规则（已完成；需求方提供的线上真实 402 响应体
    `quote_exceeded` 已逐字节入库并回归，覆盖其与两类余额错误的区分，见 §1.3 核对状态）。

## 8. 未来预留

1. **Provider 切换**：实例状态事件已发布，未来策略插件可监听它并在请求瀑布中改写 provider 路由；
   本插件不实现切换逻辑。
2. **系统消息（已调查，结论为不采用）**：宿主框架 `0.1.5` 确实提供 `system/message` surface
   事件，但它是**渲染后的系统提示词**所在的节点，不是插件通知通道——框架会在不支持 in-history
   的路由上把它置空（目标平台 ZenMux 即属此类，通知会静默失效）。因此提示消息保持 user 角色
   + plugin 来源；调查依据与后续可选做法见 `doc/设计文档/恢复流程设计.md` §6.1。
3. **新平台**：见 NFR-7 与设计文档。
